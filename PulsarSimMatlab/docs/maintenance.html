Docs maintenance

How this site is built, how it stays in step with the code, and what changed when.

How the site is built

  • Plain HTML files in PulsarSimMatlab/docs/, one shared style.css and one nav.js. No build step, no server, no internet: open docs/index.html in a browser.
  • nav.js holds the page list (PAGES) and draws the sidebar, the previous/next links and the light/dark toggle. Adding a page = one line in PAGES plus the HTML file (copy the head and the closing <script src="nav.js"> from any page).
  • api.html (function reference) is generated by docs/tools/make_api.py from the committed code (git HEAD): signatures, every argument with its default, full help texts, script headers, legacy files. Never edit it by hand. Run python3 docs/tools/make_api.py after each commit that touches functions/ or a script (--worktree reads uncommitted files instead).
  • Equations are LaTeX, rendered by KaTeX 0.16.11 (a local copy in docs/vendor/katex/, loaded by nav.js, so the site still needs no internet). Write \[ … \] inside <div class="eq"> for a display equation and \( … \) for math in the text; $ is not a delimiter. Every display equation is followed by a <dl class="where"> that defines every symbol in it: meaning, unit, and the name in the code where there is one (<dt>\(f_0\)</dt><dd>spin frequency [Hz] (<code>ephem.f0</code>)</dd>). If a symbol means something else elsewhere (τ, fref, x, K, T), say so there. On formulas.html the symbols go in a <div class="sym"> under "In words". All display equations are LaTeX (16 Oct); inline symbols in running text are partly still HTML (<var>, <sub>), which is fine. A wide equation can be split over lines with \begin{gathered} … \\ … \end{gathered}. Figures are inline SVG that use the theme colours (the svg classes in style.css), so they follow the light/dark toggle. Plots are computed by docs/tools/figures/gen_*.py from the code's formulas and constants or from a results table (list and use: tools/figures/README.md); flowcharts are written by hand in the page. Wide figures sit in <figure class="scroll"> with <svg class="wide">: on a phone they scroll sideways instead of shrinking the text.
  • Components: .callout.why (motivation), .callout.warn (caveats), .callout.note, .badge.validated / .written / .todo, .sig (function signature), .eq (formula block). Data figures colour their series with the tokens --series-1, --series-2, --series-3 (blue, orange, aqua; checked for colour-vision deficiency, in light and dark), through the SVG classes s1/s2/s3 (lines), s1f… (filled markers) and s1band, s2band (error bands). Inline code may wrap, so long file paths fit a phone.
  • Page format (agreed 13 Oct 2026): short sentences, one idea each. A page or section starts with "In short" (a .callout.note or an <h3>), then the physics, then how it works in plain numbered steps with exact formulas folded into <details>, then "Design choices": one .callout.why per choice with the alternative and why it was not taken. Reasons that are not recorded in the notes or logs are reconstructions: list them for Jasper, and add them to notes §12 only after he confirms. How to write the text itself: see writing style.

Writing style

The pages had become compact but hard to read: each sentence carried several facts, project shorthand and dates. These rules keep the text easy to follow. The excision page is the reference example.

  1. One fact per sentence. Use parentheses only for units, symbols or a name in the code. Anything else gets its own sentence, or is cut.
  2. Each section follows the same order: the problem, what goes wrong without a fix, what the code does, and what that buys, with one number.
  3. No dates, stage codes (B5b, A3a, …) or "decided by" in the explanation. The page says how things work now. History goes into a collapsed <details><summary>History</summary> at the end of the section, and into the development history and the logs. Stage codes stay in status tables and History boxes. Status badges just say validated.
  4. Define a term before using it, or link to the glossary. This includes test names and fields such as weightX, V and X(L).
  5. Every number gets a sentence that says what it means: good or bad, and compared to what. At most two numbers per sentence. Instead of a slash list ("1.02 / 1.04 / 1.08 at 10⁻³ / 10⁻⁴ / 10⁻⁶"), use a small table.
  6. Full sentences with a subject ("blankChannels writes …", not "Writes …").
  7. Say each thing once. "In short" summarizes, "How it works" explains, and the exact rules and formulas go in <details>.
  8. Test results: one sentence with the conclusion. The numbers go in a table or in <details>.

Record pages (tests, scripts, results, validation, limits, roadmap, history) are dated by nature: there rules 1, 4, 5 and 6 apply. When a page is rewritten, no number or name may disappear by accident: compare the page text before and after.

Relation to the notes

logs/current_project_notes.md is the complete reference (every number, every option); the session logs record what changed and why. This site explains: the physics, the reasoning behind each design choice, and the key results. When they disagree, the code is the truth, then the notes; fix the site.

Rule: update the docs alongside the code

From CLAUDE.md (added 8 Oct 2026): "Update docs/ alongside the code." When a function, option, default, status or result changes:

  1. Regenerate the function reference: python3 docs/tools/make_api.py.
  2. Update the stage page of that function (options, defaults, outputs, and the "why" if the reasoning changed).
  3. Update status badges: validated only after Jasper's own run.
  4. Add new results to validation record (or the stage page) and new tests to unit tests.
  5. New or changed parameters: parameters (and its "values checked against commit" line). New decisions: the decision log in development history.
  6. Update status and roadmap and the status table on the home page.
  7. If a figure shows what changed: rerun its generator in docs/tools/figures/ and replace the <figure> block, or edit the flowchart.
  8. Update the "checked against commit" line on the home page and add a line to the changelog below.
  9. Uncommitted work in progress gets at most a short "in progress" note, until it is validated and committed.
