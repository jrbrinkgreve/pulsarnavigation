Run scripts

The scripts in the PulsarSimMatlab folder. main.m runs one realization; the run*.m scripts are experiments that run the same stages many times and compare with the truth. All read their parameters from pipelineParams.m and must be run with MATLAB's current folder = PulsarSimMatlab.

In short

main.m runs the pipeline once and compares its TOAs with the truth. One run cannot show whether the error bars are honest (8–9 TOAs say little), so the experiments repeat the same stages many times, each time changing one thing on purpose: the noise, the pulsar, the signal strength or the interference. Each experiment answers one question.

Which front end the experiments use

runMonteCarlo, runSNRSweep and runH0 run the front end that frontEnd chooses. They simulate the receiver themselves, and call processIQ, then foldToTOA or detectPulsar, as main.m does. With RFI on and the full band they warn (…:noExcision), because the full band has no excision.

runRFITest (also on processIQ) and runLockedRadar (with its own superposition method) run the channel path. Besides its unit tests, the default channel path is validated end to end over seeds by runMonteCarlo.

(Until 19 Oct the first three ran on the full band only, with a …:fullBandOnly warning.)

Design choice: each experiment writes its own files

Alternative: write into data/, like main.m.

Why not: a later main.m run with skipped stages reloads files from data/. If an experiment overwrote them with another noise realization, main would pick it up. (Since 13 Oct checkConsistency would notice another noise seed.) Separate folders keep main's files untouched.

Never run two of these at once

Scripts and tests that share files corrupt each other's data when run in parallel. Examples are data/chan/, and for the unit tests data/test/chan/. An overlapping run once gave noise 72× the radiometer value (bugs and lessons #11). main.m next to a test session is safe, because the tests read only data/test/ (since 13 Oct).

main.m

Run control at the top (runStage.*, plots.*, closeFigures), then:

  1. paths and pipelineParams;, a disk estimate;
  2. sky (generator + dispersion) or reload; optional plotDispersionCheck;
  3. receiver (noise/RFI + IQ) or reload; checkConsistency. On the channel path with excision, a warning (main:brightExcision) when the pulsar is brighter than −5 dB or noise-free, because detectRFI then blanks the pulse itself (excision limits);
  4. processing up to the fold, in one call: processIQ(info_IQ, rx, ephem, proc, files, 'Reuse', ~runStage.process), with the structs from pipelineParams. It runs either the full band (dedispersion + detection) or the channels (channelizer → [detectRFI → blankChannels] → dedisperseChannels → detectChannels → [blankingWeights]), and then the fold (with NoiseCoeffs or DataWeights on the channel path). Or it reloads them, with checkProcessing and checkFold;
  5. foldToTOA (runStage.toa): TOAs, detection, good TOAs;
  6. evaluation against the truth: optional IQ, detection and fold checks (full band), validateTOA (all and good), the exact optimum (full band).

Design choice: the stages can be skipped

Alternative: always run the whole chain.

Why not: the sky stage is by far the slowest (random numbers and a 25-million-tap filter at 4 GHz) and does not depend on the noise. Changing the SNR, RFI or processing only needs the later stages. Each skipped stage reloads its info, and checkConsistency, checkProcessing and checkFold warn when files on disk were made with other parameters or from older inputs.

runMonteCarlo.m validated

The pulsar signal is fixed (sky files from main.m); only the receiver noise changes: seeds seed + (1:nSeeds), default 10. The spread of TOAs between realizations is exactly what the error bars claim to describe, so the pooled z = (TOA − truth)/σ must be N(0,1).

  • Built-in check: seed 1 = main's noiseSeed, so its TOAs must equal main's with the same frontEnd.
  • It stops with an error if the sky files do not match the parameters (checkSkyFiles: T, f_in, L, A, dutycycle, envelope mode, seed, DM, band, refFreq).
  • Per seed it runs the receiver simulation, then processIQ and foldToTOA as in main.m ('Verbose', false; its own files in data/mc/). It uses the front end that pipelineParams chooses; the default is channels, with excision and optimal weighting.
  • Pooled: validateTOA on all TOAs and on the good ones; pChi2 (mean, fraction below 0.05, Kolmogorov–Smirnov distance to uniform); detection rate (unknown phase); on the channel path the blanked fraction (false flags on pure noise).

Full band (−5 dB, 90 TOAs): rms/pred 0.950 ± 0.075, χ²red 0.91, 72 % within 1σ. pChi2 is uniform. The result was reproduced exactly on processIQ (19 Oct).

Channel path (the default: excision, optimal weighting), 50 seeds, −5 dB. The default path's error bars are honest end to end over seeds:

  • 400 TOAs, all good and detected; mean error −0.03 ± 0.15 µs;
  • rms/pred 0.956 ± 0.034; χ²red 0.915; 67.0 % within 1σ, 96.8 % within 2σ;
  • 0.0126 % of the samples blanked.

pChi2 is not uniform there at −5 dB (mean 0.29). The band-edge channels 1 and 128 hold almost no pulse in the simulation, but the fit assumes equal gain (roadmap open item 3). The excess grows with SNR²: at −15 dB pChi2 is uniform (Kolmogorov–Smirnov 0.090; ratio 0.971).

Its blind spot

The pulsar realization is the same in every run, so its self-noise is identical everywhere and missing from the scatter. Fine at −5 dB (~4 % of the variance), wrong at high SNR. That is why runSNRSweep varies the pulsar too.

  • It runs on processIQ and foldToTOA (since 19 Oct), with either front end. On the channel path:
    • excision is off for SNR points above excisionMaxSNR (−5 dB), because detectRFI would flag a bright pulse itself;
    • there is no exact optimum yet (roadmap item 8). So the detection theory and the SNR axes use the measured mean T0, the matched-filter SNR at the known phase, instead;

Design choice: H0 is a zero sky

Alternative: use a very low SNR, such as −50 dB, as "no pulsar".

Why not: −50 dB is not "no pulsar". It is a real small-antenna operating point that only needs long integrations. H0 must be a sky with no pulsar at all.

Design choice: the same random numbers at every SNR

Alternative: new pulsar and noise realizations at every SNR point.

Why not: with the same sky and noise seed at every SNR (only the noise level is rescaled), the curves against SNR are smooth: the differences between points come from the SNR, not from new random numbers. The TOAs within one SNR point stay independent, so the statistics at each point are unaffected.

runH0.m validated

Many independent noise-only profiles to test the H0 side of detectPulsar and the noise covariance model behind it (and behind the TOA error bars).

  • nPass (100) passes. The zero sky is made once; the receiver noise gets seed seed + 10000 + i, which does not overlap with the sweeps. The processing is the same as main's: processIQ, then detectPulsar, on the front end that pipelineParams chooses (since 19 Oct; before, full band only). A pass gives 9 complete turns on the full band (~8 s), and 8 on the channel path (~40–55 s).
  • Collects T0, Tmax, noiseRatio, the circular autocorrelation of each normProfile, and the model correlation from weightX: full band lag 1; channel path lags 1–3 of the combination detectPulsar uses (optimal: weights 1/variance per channel; equal noise levels assumed). With excision also the blanked fraction per pass: on pure noise, the false-flag rate of detectRFI.
  • Exceedances at PFA 10⁻¹, 10⁻², 10⁻³; saves data/mc/h0Run.mat; figure.

Motivation. The phase E sweep gave a T0 standard deviation of 1.10 ± 0.075 under H0, and error-bar ratios of 1.03–1.06, all from the same 10 noise realizations. That could have been a 5–10 % hole in the noise model.

Outcome. The T0 standard deviation is 1.008 ± 0.024; the lag-1 correlation is 0.2484, against 0.2501 modelled; there is nothing beyond lag 1. So the noise model is complete, and the earlier hint was a fluctuation of the shared realizations.

Channel path (19 Oct; excision, optimal weighting; 100 passes, 800 profiles). The default path's detection statistics are calibrated end to end. T0 has mean +0.033 ± 0.035 and standard deviation 1.023 ± 0.025. The lag-1 correlation is 0.2567, against 0.2580 modelled, and lags 2–3 are ≈ 0. runRFITest.m validated

The cases are: noise only, each source of rfiScenario alone, and all five. For each case the receiver stage runs with that RFI and main's noise seed, so the noise is the same in every case. Then the channel path runs twice, without and with excision, both with optimal weighting. Each pass is processIQ (with excision false or true; the filterbank runs in each), then foldToTOA.

The output is a table: blanked fraction, good TOAs, median SNR, median TOA error, rms/pred, median χ², total offset. The script requires frontEnd = 'channels', and stops if main's sky files do not match the parameters (checkSkyFiles).

Results: RFI excision. They are saved to data/rfi/runRFITest_results.mat, the reference that expSimRFI reads. With calPass = true they go to runRFITest_results_cal.mat instead (since 21 Oct), so a calibration run keeps the reference.

Rotating radar cases (8–11). They use the scenario radar on a rotating antenna (10 s scan, 39 ms beam). One case has a beam passage centred in the file (−30 dB floor); three have sidelobes only (beam 5 s away), at −25, −30 and −35 dB. For pulsed sources the table adds two columns, from the source's parameters (ground truth, for validation only): the fraction of its pulses blanked in its own channels, and the fraction of its energy in missed pulses. runCases picks a subset of the cases.

LTE cases (12–13): the 'noise' type, 20 MHz wide at 1472 MHz (inside LTE band 32), at INR −10 and 0 dB. Results: receiver and excision limits.

Realistic scenario (14–15). Case 14 is rfiRealistic (~3 min). Case 15 is the same, but with Inmarsat as ten narrow (200 kHz) carriers inside channels 105–114, instead of three wide blocks (~5 min): the worst case for the TOA error bars. A case can also be given as {sources, label}. The excision path also runs periodicRFI when periodicMask is true, as main.m does.

Per-channel noise check (every case; evaluation only). For each channel, r is var/mean² of the off-pulse fold bins (more than 3 FWHM from the pulse), divided by the median channel's. r = 1 means the channel behaves like the model. The table gets two columns:

  • the number of channels with r > 1.1;
  • how much the TOA error bars are too small because of them: √(ΣF r/ΣF) − 1, with F = 1/ac², the fit's channel weights.

After the table, each run with excision lists two kinds of channels: those with r > 1.1, and those whose flagged windows exceed 10× the expected false flags and 3× the median channel's. It names the sources covering them (ground truth, for labels only), and the periodic emitters found. The check is valid only when little is blanked, because r compares with the median channel, not with the blanking-aware model. Results: results.

runLockedRadar.m

A radar with PRF 400 Hz = 4·f0 puts one pulse per turn on the pulse flank. Whatever excision leaves of it folds coherently into the profile. This script measures how much. It stops if main's sky files do not match the parameters (checkSkyFiles).

  1. Receiver runs: reference (no radar) and with the locked radar (0.1 µs and instant edges). Radar run − reference = the radar alone (the chain is linear).
  2. Per case: mask from the full data; reference, radar-only and full data all go through the same blanking, dedispersion, detection and fold with the same weights.
  3. Leftover L(φ) = folded radar-only power / channel baseline.
  4. TOA bias at −5 dB: full data − reference (same noise), cross-checked with reference + leftover.
  5. Bias at weak SNR: noise-free folds ρ·template + L through estimateTOA, ρ from −5 to −60 dB; the ρ where the bias reaches 1 µs.
Design choice: measure the leftover in baseline units, not as a TOA error

Alternative: measure the TOA error caused by the radar at −5 dB.

Why not: the pulsar is ~80,000× weaker at −54 dB than at −5 dB, so a TOA test at −5 dB says little about the target. The leftover in units of the noise baseline does not depend on the pulsar, and comparing it with the pulse height ρ gives the bias at any SNR from one run.

The cases are rows of caseList = [radar, excision, frequency guard, periodic mask]. The radars are: 0.1 µs edges, instant edges, and the 0.1 µs radar on a rotating antenna, seen only through −35 dB sidelobes. Cases 9–12 compare excision with and without the periodic mask. runCases picks a subset, and only the radars it needs are simulated.

runScenario.m

The reference scenario with the fast simulator:

  • B0329+54 from the Netherlands (52° N, passes of 19.6 h above 20°), and J0437 from 30° S (passes of 12.3 h);
  • nominal and worst-case flux, dual polarization, and 128 channels with the band-edge taper;
  • profiles: B0329+54 with five Gaussian components (NBin 2048); J0437 with eight components fitted to its measured Parkes profile (NBin 1024; since 21 Oct, before that a single Gaussian, whose results are kept as *_singleGauss512.mat).

In plain steps:

  1. Daily passes from latitude, declination and the 20° elevation mask, one per sidereal day.
  2. Each pass is cut into chunks for memory (2 h for B0329+54, 24 h for J0437) on the sub-int grid, and simulateFold draws the folds. The sub-ints are 120 s for B0329+54 and 300 s for J0437.
  3. adaptiveSubints merges sub-ints until SNR ~7 (also over the gap to the next day); the sub-ints of the group still open at the end of a chunk are carried into the next one, which is exact because fold sums add.
  4. foldToTOA on every closed group; the TOA against the truth.

Per case it reports: good TOAs per day, hours of data per TOA, calendar span, σ (and c·σ), the honesty of the error bars, χ², the data left over, and the figure of merit σ·√hours.

The true pulse sits 0.1 FWHM from the predicted phase. adaptiveSubints judges the SNR at the predicted phase, which assumes a good ephemeris; a first test with an offset of 0.12 turns closed no group at all.

With motion.on the truth is that of a receiver that is not where the observer thinks it is (block D3c):

  • The observer keeps the assumed site. The true site is 100 km east of it by default (motion.offsetENU).
  • The clock is perfect, or an SDR's: the crystal's noise and a rate within ±2 ppm. The observer knows the rate to 10⁻⁹ and the offset to 1 ms.
  • Each sub-integration's pulse is shifted by trueResiduals' phase offset at its reference time.
  • The scenario's start is moved to the first real transit after 1 March 2026, so that the daily sine has its physical phase relative to the passes.
  • Each TOA records its absolute time, the measured residual and the true one, split into position and clock: the input of the navigation fit. The result files get the suffix _motion_perfect or _motion_sdr.
  • A TOA merges sub-ints, often over hours and sometimes over two passes a day apart, so it is a time-average. Its true parts and the clock estimate the observer used are averaged over its sub-ints. Its time tag is the time nearest its mean time whose sidereal phase is the circular mean of its sub-ints' (sideTag), clamped to their span. It also carries its sub-ints' times (tSub), so that the navigation fit can average its row the same way.
  • With the SDR clock the observer tracks it (motion.track "daily"). After each day it fits all its TOAs so far with navFit and the clock model, predicts its clock for the next day, and folds that day with the prediction. Until it has 20 TOAs, about two days, it keeps the calibration from port. "none" keeps the calibration throughout; those files get the suffix _notrack.

A 6-day check with the SDR clock (true rate −1.17·10⁻⁶): the rms of the clock the observer had not estimated, per day. The pulse is 6.6 ms wide.

The variants are clean, RFI, RFI + calibration, + scintillation, and fixed groups for comparison. Results: scenario.

runShip.m

A ship that navigates by pulsars: the fast simulator and the navigation filter in a closed loop (block D4d). The ship knows its track only from dead reckoning, and an unknown current pushes it off that track.

SettingDefault
RouteFrom 50° N, 5° W, heading 250°, 5 knots, 14 days
CurrentA mean drawn with 0.3 m/s per axis, plus a wander of 0.1 m/s that reverts to the mean over about 2 days
PulsarsB0329+54 with five components (NBin 2048, 120 s sub-integrations) and B0950+08 as one Gaussian (W50 8.6 ms, 100 mJy, NBin 512, 300 s), in simultaneous beams
ClockThe SDR's crystal with a rate within ±2 ppm. The port calibration is off by a drawn 1 ms and 10⁻⁹.
Start"self", or "calibrated": the per-pulsar constants known from port

Other runs set shipOpts before calling the script, with any of the fields nDays, flux, seed and start. The seed draws the current, the clock and every fold's noise.

In plain steps:

  1. The truth: the dead-reckoning track is a rhumb line. The true track adds the current's drift in the ship's own east and north directions.
  2. Each day, each pulsar is folded whenever it is above 20° at the ship's dead-reckoning position. The observer folds with its current track and clock estimate. The simulator puts each sub-integration's pulse where the true track and clock put it.
  3. adaptiveSubints and foldToTOA give the TOAs. Each TOA keeps its sub-integrations' times and the observer's reference values for them. The filter averages each TOA's row over those times, as the TOA itself is averaged.
  4. Each evening the observer runs navFilter on all its TOAs so far, referred to the dead-reckoning track and the port clock. It folds the next day with the corrected track and clock.
  5. After the last day: the smoother over all TOAs against the truth, and its twin. The twin is the same smoother on ideal TOAs, the truth plus Gaussian noise of the stated size. A difference between the two comes from the TOA chain, not from the filter.

It prints a daily table (TOAs per pulsar, the dead-reckoning error, the observer's error one day ahead, the clock it had not estimated) and the final errors and pulls. The result goes to data/scenario/ship_14d_nominal.mat, with _cal for a calibrated start and _seed<n> for other seeds. Results: navigation.

The processing in the scripts

The processing is factored out into processIQ (IQ in, fold out) and foldToTOA (TOAs, detection, good TOAs). main and the voltage-chain scripts use both, except runLockedRadar, which processes difference channels by superposition (roadmap). runScenario and runShip do not call processIQ: the fast simulator draws their folds, and they form TOAs with adaptiveSubints and foldToTOA.
