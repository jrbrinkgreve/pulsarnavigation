PulsarSimMatlab · documentation

Navigating by pulsars

A MATLAB pipeline that simulates a pulsar's radio signal through interstellar space and a small radio receiver, then turns the raw receiver voltages back into pulse arrival times (TOAs) with honest error bars. Every processing step is checked against the simulation's ground truth.

Start with the physics → See the pipeline Parameters

The idea. A pulsar sweeps a radio beam past us once per turn, with a period stable to better than a microsecond over years. Knowing where you are, you can predict when each pulse arrives. Turned around: a pulse that arrives early means you are closer to the pulsar along that direction, by the speed of light times the difference. Arrival times from four or more pulsars in different directions give a 3-D position plus a clock offset, like GNSS with natural beacons. This project builds the part that turns raw antenna voltages into those arrival times.

What makes this hard

The pulse is noiseNo waveform to correlate with: the information is in the power, so the processing squares, then folds. It is extremely weak~54 dB below the noise on the target hardware. One pulse is invisible; a TOA takes hours. The sky smears itInterstellar electrons spread each pulse over 6.3 ms across the band. It must be undone exactly. Interference is far strongerOne radar pulse outweighs ~80,000 pulsar pulses: it must be blanked, not reduced. Error bars must be honestA navigation filter trusts the stated σ. Much of the code exists to make it exact.

Quick start

  1. Open MATLAB in the PulsarSimMatlab folder (paths in pipelineParams.m are relative).
  2. Edit parameters in pipelineParams.m; see parameters.
  3. In main.m, choose the stages to run (runStage.*) and the check plots (plots.*). The sky stage is slow and independent of the noise; set it to false once its files exist.
  4. Run main. It prints a disk estimate, each stage's progress, the TOAs, the detection result and the validation against the truth.

Disk use is large: about 61 GB per second of simulated data at 800 MHz; the default L = 0.1 s needs roughly a tenth of that. See run scripts.
