Conventions and why

Rules every stage follows. Each one exists because something would otherwise go wrong: a pipeline that only works on simulated data, out-of-memory errors, silent timing offsets, or results that cannot be reproduced.

The ten rules
  1. The processing uses only what a real observer knows: the ephemeris and the receiver settings.
  2. Every stage streams file to file in blocks; memory never grows with the file.
  3. Data files are headerless float32; their description is in an _info.mat next to them.
  4. Each stage hands its settings to the next through that info struct.
  5. Times are double precision, computed from absolute sample indices.
  6. Every random process has its own seeded stream.
  7. Options are name-value pairs; filters are built by hand, without a toolbox.
  8. One parameter file serves main.m and every experiment (the tests have a frozen copy).
  9. A new option leaves the default output unchanged, bit for bit.
  10. One stage at a time, explained first, validated by Jasper's own run.

The first rule protects what the results mean; rules C2–C4 keep the data flowing; C5 and C6 keep every number exact and reproducible; C7–C10 keep the code and its history under control.

C1 · The ground-truth rule

Processing stages use only what a real observer would know: the ephemeris (the ephem struct: f0, F1, TRef, DM, profileFWHM), and the receiver settings (band, LO frequency, sample rate, taken from the receiver's info). The ground truth (info_gen, info_disp, info_rx: true pulse times, noise level, RFI parameters) is used only by the simulation stages and by the check and validation functions (Figure C.1).

For a moving receiver the same split holds. The observer predicts its pulses from the trajectory it assumes and from its own clock estimate (makePredictor, stage 7a). The true trajectory and the true clock (trueResiduals, makeClock) belong to the truth: only the fast simulator uses them, to place the pulses, and keeps them in its separate truth struct (fast simulator).

The processing must later run unchanged on real receiver data, where there is no truth. A stage that quietly used the true noise level would look perfect in simulation and fail on the sky. The rule also keeps validation meaningful: comparing a result with the truth only proves something if the truth was not used to make it. Examples of the rule in action:

  • The TOA noise model uses the fitted baseline and amplitude, not the simulated noise level.
  • main.m passes the noise bandwidth of the observer's own dedispersion taper (391.6 MHz), not the product of both tapers (389.6 MHz), because the observer does not know the simulator's dispersion taper.
  • detectRFI uses only the channel data and the channelizer settings, never the RFI parameters.
  • expectedPowerModel, which uses all the truth, is only called by plot checks and to print the best achievable precision.

C2 · Streaming file I/O

Every stage is file in → file out, streamed in blocks: read a block of samples from the input file; process it (filters that reach across blocks keep the overlap they need); write the result and check that every sample was written. Memory is bounded by the block or FFT size, never by the file size. Filters that span many samples (the dispersion kernel has 126 million taps at the default DM 25) use FFT convolution with overlap-add (forward dispersion, IQ filter) or overlap-save (dedispersion), with the FFT size chosen automatically to minimise the total cost within a MaxMemoryGB limit.

Whole signals cannot be held in memory: one second of simulated data at 4 GHz is 16 GB per real file, and a one-second run writes about 61 GB of files on the full band and about 72.5 GB on the default channel path with excision (sizes per stage), against 24 GB of memory. Streaming also mirrors how real recorded data would be processed. Checking every fwrite count prevents the worst failure: a run that "succeeds" on a half-written file because the disk was full.

Headerless float32 is what software-defined radios and pulsar recorders commonly write, and any tool can read it. Float32 halves the disk use of double, and its precision is no problem for sample values; times are never stored in float32 (Section C5). The description of each file (rate, size, format, how it was made) lives in its info struct.

C4 · Info structs

Every stage returns an info struct and saves it as <outputname>_info.mat next to its data file. The next stage takes its input file and sample rate from that struct (info.file, info.actualFsOut, …), and when main.m skips a stage, it reloads the struct with loadInfo(dataFile). Common fields: file, inFile, precision, byteOrder, isComplex, N, fs, actualFsOut, stage-specific parameters and conventions, elapsed.

Passing parameters by hand from one stage to the next invites mismatches, such as the wrong sample rate after decimation or the wrong LO. Chaining through info means each stage describes exactly what it wrote, and it makes stale files detectable (Figure C.2):

  • main.m's checkConsistency warns when files on disk were made with different parameters. For the sky files (via checkSkyFiles) it compares T, f_in, L, A, dutycycle, envelope mode, seed, DM, band and refFreq. For the receiver files it compares SNR, receiver input, RFI sources, noise seed, fLO, fs and filter order.
  • checkProcessing and checkFold, local functions of processIQ, do the same for reused processing and fold files. Each file must be made from the file before it, must not be older than it, and must have the same f_out, DM, refFreq, band, chanWidth, nBin, turns per sub-int, ephemeris and data weights.

C5 · Time and precision

  • Times are computed in double precision from absolute sample indices. Sample k (0-based) of a stream at rate fs is at time k/fs (plus T0, currently 0).
  • Oscillator and chirp phases are computed from the absolute index too, never accumulated sample by sample.
  • Filters have odd length or a known delay, and their group delay is removed exactly. Decimation keeps samples on the global grid: output sample k ↔ input sample k·D.
  • A detected time bin's time is the centroid of its samples: tk = binTime0 + (k−1)·binDt.

Float32 rounds a time to ~60 ns at t = 1 s, and running sums such as t += 1/fs drift (Figure C.3). The project measures TOAs to sub-microsecond precision and wants nanoseconds later, so every timing convention must be exact. Times from the absolute index also do not depend on the block size a stage happens to stream with. An unremoved filter delay of 256 ns was a real bug once (bugs and lessons #5).

Each random process has its own private RandStream; the global random number generator is never touched.

The same seed gives identical data, independent of block sizes. With one global generator (rng(seed)), every draw would depend on every other. Separate streams let you change the noise without changing the pulsar (Monte Carlo over noise seeds), or rerun one stage alone. Block-size independence means a change of memory settings can never change the data, and substreams for RFI make each chip chunk or burst depend only on its own index.

C7 · Arguments and toolboxes

Required inputs are positional; everything else is a name-value option in an arguments block (MATLAB R2019b+; mustBeTextScalar needs R2020b+). No Signal Processing Toolbox: the filters (Kaiser-windowed sincs, raised-cosine tapers, the polyphase filterbank) are built by hand. Hand-built filters are fully understood and fully specified in the code: tap count, stopband, delay and gain convention are all visible, and there is no toolbox dependency.

C8 · One parameter file

pipelineParams.m is a script that defines every parameter (pulsar, simulation, receiver, noise and RFI, processing, ephemeris, file names). main.m and all run*.m scripts call it, so its variables land in their workspace; with parameters set inside each script, the main run and the Monte Carlo scripts would drift apart. Later the file will be split into simulation parameters (truth) and observation parameters (receiver, processing) for real data. The unit tests are the exception: they run their own frozen copy, tests/testParams.m, with their data in data/test/ (tests), because their bit-for-bit regressions belong to one fixed configuration.

Monte Carlo and test scripts write to their own files (data/mc/, data/rfi/, data/locked/), so a later main.m run with skipped stages never picks up a Monte Carlo realization. checkConsistency would also notice another noise seed.

C9 · Bit-identical regressions

When a function gains a new option, the default behaviour must reproduce the old output bit for bit. Reference outputs are frozen before the change (tests/make*Reference.m), and the unit test compares against them. A tolerance would hide accidental changes; bit for bit means validated numbers stay validated. If the full-band path, validated in block 1, still gives exactly the same bits after all of block A, nothing in it needs re-validation.

C10 · Working style

From the project's CLAUDE.md:

  • go one stage at a time;
  • explain the physics and the planned change before editing;
  • one logical change per edit;
  • Jasper runs MATLAB; a result is validated only after Jasper's own run;
  • after each session a dated note goes into logs/, and docs/ is updated alongside the code.

Session logs record what changed and why; logs/current_project_notes.md is the complete reference. The next page, the pipeline overview, shows how the stages that follow these rules fit together.
