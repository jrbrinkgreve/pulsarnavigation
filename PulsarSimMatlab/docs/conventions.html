Conventions and why

Rules every stage follows. Each one exists because something would otherwise go wrong: out-of-memory errors, silent timing offsets, results that cannot be reproduced, or a pipeline that only works on simulated data.

1. The ground-truth rule

Processing stages use only what a real observer would know: the ephemeris (the ephem struct: f0, F1, TRef, DM, profileFWHM) and the receiver settings (band, LO frequency, sample rate, taken from the receiver's info). Ground truth (info_gen, info_disp, info_rx: true pulse times, noise level, RFI parameters) is used only by the synthetic stages and by the check and validation functions.

Why

The processing must later run unchanged on real receiver data, where there is no truth. If a processing stage quietly used the true noise level or the true pulse times, it would look perfect in simulation and fail on the sky. The rule also keeps validation meaningful: comparing a result with the truth only proves something if the truth was not used to make it.

Examples of the rule in action:

  • The TOA noise model uses the fitted baseline and amplitude, not the simulated noise level.
  • main.m passes the noise bandwidth of the observer's own dedispersion taper (391.6 MHz), not the product of both tapers (389.6 MHz), because the observer does not know the simulator's dispersion taper.
  • detectRFI uses only the channel data and the channelizer settings, never the RFI parameters.
  • expectedPowerModel, which uses all the truth, is only called by plot checks and to print the best achievable precision.

2. Streaming file I/O

Every stage is file in → file out, streamed in blocks. Memory is bounded by the block or FFT size, never by the file size. Every fwrite count is checked, so a full disk raises an error instead of leaving a truncated file.

Why

One second of simulated data at 4 GHz is 16 GB per real file; a full run uses about 61 GB of files. Nothing fits in the 24 GB of memory at once. Streaming also mirrors how real recorded data would be processed. Checking write counts prevents the worst failure mode: a run that "succeeds" on a half-written file.

Filters that span many samples (dispersion kernels of 25 million taps) use FFT convolution with overlap-add (forward dispersion, IQ filter) or overlap-save (dedispersion). The FFT size is chosen automatically to minimise total cost within a MaxMemoryGB limit.

Why headerless float32

It is what software-defined radios and pulsar recorders commonly write, any tool can read it, and float32 halves the disk use of double. Precision is not an issue for sample values; times are never stored in float32 (see time).

4. Info structs

Every stage returns an info struct and saves it as <outputname>_info.mat next to its data file. The next stage takes its input file and sample rate from that struct (info.file, info.actualFsOut, …). When main.m skips a stage it reloads the struct with loadInfo(dataFile).

Common fields: file, inFile, precision, byteOrder, isComplex, N, fs, actualFsOut, stage-specific parameters and conventions, elapsed.

Why

Passing parameters by hand between stages invites mismatches (the wrong sample rate after decimation, the wrong LO). Chaining through info means each stage describes exactly what it wrote. It also makes stale files detectable: main.m's checkConsistency warns when files on disk were made with different parameters (sky, via checkSkyFiles: T, f_in, L, A, dutycycle, envelope mode, seed, DM, band, refFreq; receiver: SNR, receiver input, RFI sources, noise seed, fLO, fs, filter order; the sky parameters A to refFreq, the noise seed and the filter order since 13 Oct 2026); since 13 Oct 2026 checkProcessing and checkFold do the same for reused processing and fold files (made from the file before them, not older than it, same f_out, DM, refFreq, band, chanWidth, nBin, turns per sub-int, ephemeris and data weights).

5. Time and precision

  • Times are computed in double precision from absolute sample indices. Sample k (0-based) of a stream at rate fs is at time k/fs (plus T0, currently 0).
  • Oscillator and chirp phases are computed from the absolute index, never accumulated sample by sample.
  • Filters have odd length or known delay, and their group delay is removed exactly; decimation keeps samples on the global grid (output sample k ↔ input sample k·D).
  • A detected time bin's time is the centroid of its samples: tk = binTime0 + (k−1)·binDt.
Why

Single precision rounds to ~60 ns at t = 1 s, and accumulated phases drift. The project measures TOAs to sub-microsecond precision and wants nanoseconds later, so every timing convention must be exact. An unremoved filter delay of 256 ns was a real bug once (bugs and lessons #5).

6. Reproducibility

Each random process has its own private RandStream; the global random number generator is never touched.

Pulsar signalmt19937arseed (42)

RFImrg32k3a substreamsper chip chunk / per burst

The same seed gives identical data, independent of block sizes.

Why

Separate streams let you change the noise without changing the pulsar (Monte Carlo over noise seeds), or rerun one stage alone. Block-size independence means a change of memory settings can never change the data. Substreams for RFI make each chip chunk or burst depend only on its own index.

7. Arguments and toolboxes

Required inputs are positional; everything else is a name-value option in an arguments block (MATLAB R2019b+, mustBeTextScalar needs R2020b+). No Signal Processing Toolbox: filters (Kaiser-windowed sincs, raised-cosine tapers, polyphase filterbank) are built by hand.

Why

Hand-built filters are fully understood and fully specified in the code: tap count, stopband, delay and gain convention are all visible. It also avoids a toolbox dependency.

8. One parameter file

pipelineParams.m is a script that defines every parameter (pulsar, simulation, receiver, noise and RFI, processing, ephemeris, file names). main.m and all run*.m scripts call it, so its variables land in their workspace. The unit tests are the exception: they run their own frozen copy, tests/testParams.m, with their data in data/test/ (13 Oct 2026, tests).

Why

The main run and the Monte Carlo scripts cannot drift apart. Later it will be split into simulation parameters (truth) and observation parameters (receiver, processing) for real data. The tests must not follow edits: their bit-for-bit regressions belong to one fixed configuration.

Monte Carlo and test scripts write to their own files (data/mc/, data/rfi/, data/locked/), so a later main.m run with skipped stages never picks up a Monte Carlo realization (and since 13 Oct checkConsistency would also notice another noise seed).

9. Bit-identical regressions

When a function gains a new option, the default behaviour must reproduce the old output bit for bit. Reference outputs are frozen before the change (tests/make*Reference.m), and the unit test compares against them.

Why

Validated numbers stay validated. If the full-band path, validated in block 1, still gives exactly the same bits after all of block A, nothing in it needs re-validation. "Close enough" would hide accidental changes.

10. Working style

From the project's CLAUDE.md: go one stage at a time; explain the physics and the planned change before editing; one logical change per edit; Jasper runs MATLAB; a result is validated only after Jasper's own run; after each session a dated note goes into logs/, and docs/ is updated alongside the code. Session logs record what changed and why; logs/current_project_notes.md is the complete reference.
